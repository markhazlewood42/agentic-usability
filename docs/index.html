Working Framework

Agent Usability Heuristics

What are the qualities of an API or CLI interface that make it easier or harder for an agent to reason about and use effectively?

Mark Hazlewood, Staff Product Designer, HubSpot Developer Product Group
v0 — May 2026 · Source

Why this framework

Nielsen wrote his 10 usability heuristics in 1994 for human users of GUIs. There is no equivalent canon for agents as consumers of APIs, CLIs, and tool surfaces.

Two things changed at once in 2025-2026. Agents became real consumers of API and tool surfaces (MCP, tool-use connectors, multi-step agent workflows). And platforms began committing to full API parity, meaning every product capability needs an API surface. That combination means APIs now have two distinct readers: human developers and AI agents. The constraints on each are different.

Some of what makes a surface usable for humans helps agents (consistent naming, good errors, clear scopes). Some doesn't (visual hierarchy, terse human-readable copy). Some things help agents specifically and barely register for humans (typed errors over prose, lean response shapes, self-describing schemas). This framework names the differences.

The 10 heuristics

Each heuristic includes a rule, why it matters for agents specifically, and what failure looks like.

H1 Discoverability without trial-and-error Reason-about

The agent can find the right capability from a description of intent, not by trying things until something works.

Why for agents: Humans skim and recover from wrong choices visually. Agents recover by retrying, which is expensive in tokens and dangerous in side effects. Fails when: Two endpoints with overlapping responsibilities, no clear signal which is canonical. Names don't match the agent's natural framing of intent.

H2 Predictable shapes Reason-about

Inputs and outputs are typed, deterministic, and consistent. The same concept has the same shape across the surface.

Why for agents: Agents pattern-match on shapes more than humans do. A contact that looks one way in one endpoint and another way three calls later is a hallucination magnet. Fails when: Pagination differs between resources. Date formats vary. ID fields named inconsistently.

H3 Self-describing surface Reason-about

Every endpoint, tool, or command returns enough metadata to be understood without out-of-band documentation.

Why for agents: Agents have no prior context unless it was injected into the prompt. A self-describing surface lowers the cost of cold-start use. Schemas, examples, annotations, and inline help are first-class. Fails when: OpenAPI spec exists but isn't loadable by the agent. MCP tool descriptions are one-liners.

H4 Errors that are machine-actionable Use-effectively

Errors are typed, coded, and include structured recovery information. Prose alone fails.

Why for agents: Humans read "Sorry, that didn't work" and infer intent. Agents read it literally and either retry blindly or hallucinate a fix. An error is a second-chance prompt: a structured error that names the problem, lists valid options, and points to relevant docs enables near-100% recovery. Fails when: All errors are 500s with a string body. Validation errors don't identify the offending field.

H5 Composability Use-effectively

Outputs of one operation match inputs of related operations without translation.

Why for agents: Multi-step agent workflows chain calls. Every translation step (IDs, formats, references) is a place to fail. A composable surface lets the agent move data between calls without reshaping. Fails when: "List" returns IDs in one shape, "Get" wants a different shape. Reference fields aren't directly callable.

H6 Idempotency and safe retry Use-effectively

Operations declare their idempotency. Agents can retry on failure without guessing at side effects.

Why for agents: Agents retry. A lot. If the platform doesn't tell the agent which operations are safe to retry, the agent will either over-retry (duplicates) or under-retry (give up too easily). Fails when: No idempotency keys on writes. POST that's actually upsert, not documented as such.

H7 Token economy Use-effectively

Responses are lean by default and expandable on request. No mandatory bloat.

Why for agents: Every byte of response goes into a context window the agent has to pay for. A 50-field object when the agent needed two fields is taxation by API design. Fails when: No field selection. Default response includes deeply nested associations. Pagination defaults to absurdly large pages.

H8 Scoped intent Use-effectively

Authorization is granular and intelligible up front. The agent knows what it's allowed to do before it tries.

Why for agents: A 403 mid-flow is a debugging nightmare for an agent. Agents need to know the boundaries of their authority at the start, in machine-readable form, and react to scope changes cleanly. Fails when: Scopes aren't visible to the agent. Scope names don't match capability names. Failure mode is generic 403 with no hint about which scope is missing.

H9 Naming as IA Reason-about

Names carry meaning. Similar things are named similarly. The lexicon agents see in tool/endpoint names matches the lexicon humans see in docs.

Why for agents: Agents lean on names harder than humans do because they often pick a tool from a name alone. Naming is the first and most-used affordance. Empirically, tool names have stronger influence on agent selection than descriptions (ToolTweak, 2025). Fails when: The same concept has three names. Internal jargon leaks into public names.

H10 Observability and audit Use-effectively

Every action an agent takes is traceable, attributable, and visible to the customer in real time.

Why for agents: Agents operate at scale. One mistake propagates fast. Customers and admins need to see what an agent did, when, and on whose authority, both for trust and for recovery. Fails when: Agent actions aren't distinguishable from user actions in audit logs. No per-agent attribution.

How the heuristics cluster

The core research question splits into two halves: "easier or harder to reason about" and "easier or harder to use effectively." Agent failure modes cluster differently across the two.

Reason-about

Predict the surface before calling it. Failures show up as picking the wrong call or hallucinating shape.

  • H1 Discoverability
  • H2 Predictable shapes
  • H3 Self-describing surface
  • H9 Naming as IA

Use-effectively

Act on the surface and recover well. Failures show up as runtime errors, retry storms, scope mismatches, and trust gaps.

  • H4 Machine-actionable errors
  • H5 Composability
  • H6 Idempotency
  • H7 Token economy
  • H8 Scoped intent
  • H10 Observability

Key concepts

Vocabulary the framework builds on. Each concept either originates in the literature (cited) or is a synthesis the framework owns.

Agent-Computer Interface (ACI)

The designed surface an agent reads, calls, and interprets. Coined by Yang et al. (SWE-agent, 2024). Interface design alone, independent of the model, materially lifts task success.

Schema-as-prompt

Every field name, type, and enum value in a tool schema is consumed by an LLM as natural language. There's no separation between "API contract" and "instructions to the model." The contract is a prompt fragment.

Tool name as primary affordance

Empirically, tool names have stronger influence on agent selection than descriptions (ToolTweak, 2025). Rename-not-redocument is the higher-leverage intervention.

Context economy

Every token in a tool spec or response payload competes for finite context window space. Information density per token is a usability axis, the way visual hierarchy is for human UIs.

Error as second-chance prompt

Errors aren't just diagnostics. They're another input to the agent's next decision. A structured error enables ~100% recovery. A 500 with a string body forces blind retry or hallucination.

pass^k reliability

From τ-bench (Yao et al., 2024): the probability the agent succeeds consistently across k attempts. Frontier agents: pass^1 ≈ 50%, pass^8 < 25%. The gap is the reliability tax, much of it attributable to interface ambiguity.

Reliability tax

Framework-coined term. The amount of agent failure attributable to interface ambiguity rather than model capability. Improving the surface reduces the tax even when the model stays the same.

Surface vs. capability

A platform can fetch contacts (capability). Its particular set of endpoints, parameter names, error shapes, and docs is the surface. Most benchmarks measure both tangled together. This framework separates them.

Position relative to existing work

Where this framework sits in the landscape. Not a replacement for any of these, but a distinct contribution.

Framework Relationship
Nielsen's 10 (1994) Mirror the format and derivation method. Extend from human GUI to agent-facing surfaces.
Cognitive Dimensions Borrow dimensional thinking. Several CDs translate cleanly (viscosity, hidden dependencies, role-expressiveness).
Clarke API-CD (2004) Direct academic ancestor. Clarke did persona-driven API usability for humans. This does it for agents.
Bloch (2006) Bridge insight: "Every API is a little language." Agents read that language as a prompt, not as documentation.
MS HAX (2019) Different subject. HAX guides how agents act on humans. This guides how humans build surfaces for agents.
Anthropic Writing Tools Most direct contemporary. This extends with persona conditioning, cross-surface scope (API+CLI+MCP), and governance as a first-class dimension.
SWE-agent / ACI Adopt the "ACI" term. Provide the heuristics for designing a good one across API, CLI, and MCP.
12-Factor Agents Application-level analogue. This framework is one layer below: the surface, not the agent app.

Top references

The 10 most important sources, in reading order. Full annotated bibliography in the repo.

  1. Yang et al. (2024). SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering. NeurIPS 2024. Coins "ACI" and shows interface design alone lifts task success. arXiv
  2. Anthropic. Writing Effective Tools for AI Agents. Eight principles for tool design. The most direct competing artifact. Link
  3. Yao et al. (2024). τ-bench: Benchmarking Tool-Agent-User Interaction. Introduces pass^k. Frontier agents succeed <50% consistently. arXiv
  4. Nielsen, J. (1994). Enhancing the Explanatory Power of Usability Heuristics. The derivation method (factor analysis of 249 problems) is the credibility template.
  5. Clarke, S. (2004). Describing and Measuring API Usability with Cognitive Dimensions. The human-API precursor. Persona-driven API usability studies at Microsoft Research. PDF
  6. Bloch, J. (2006). How to Design a Good API and Why It Matters. "Every API is a little language." Agents read that language as a prompt. Link
  7. Anthropic. Code Execution with MCP: Building More Efficient AI Agents. Agent usability as a system architecture choice, not just tool design. Link
  8. Horthy, D. 12-Factor Agents. Application-level reliability principles. This framework is one layer below. GitHub
  9. Luo et al. (2025). MCP-Universe: Benchmarking LLMs with Real-World MCP Servers. Frontier models score 33-44% on MCP tasks. arXiv
  10. Willison, S. The Lethal Trifecta for AI Agents. Private data + untrusted content + external comms = structural exfiltration risk. Link
